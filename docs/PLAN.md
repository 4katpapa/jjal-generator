## 1. 목표

커뮤니티에 올리는 PC 사양 자짤(기준 850×300)을 만드는 편집기를 새 바탕에서 만든다.

| 기존 앱의 불편 | 새 앱의 목표 |
|---|---|
| 직관성이 떨어지고 사용법이 복잡함 | 화면의 모든 요소가 레이어 목록에 보이고, 고른 레이어의 속성만 옆에 뜬다 |
| 요소 제어가 의도대로 안 되거나 불가능함 | 모든 요소를 같은 방식으로 이동·크기·회전·순서 변경·숨김·잠금 한다 |
| 수치를 바꿔도 변화가 안 보임 | 조절한 값은 화면에 바로 반영되고, 반영이 제한될 때는 그 자리에서 이유와 실제 적용값을 보여준다 |
| 프리셋을 바로 쓰기 애매함 | 프리셋은 한 번 클릭으로 내 사양·닉네임·이미지가 들어간 완성 상태가 되고, 적용 후에는 일반 레이어로 자유롭게 고친다 |

## 2. 기존 앱 확인 결과

**무엇인가.** Electron 데스크톱 앱 + 같은 코드를 쓰는 웹판(jjaltool.kro.kr). PC 사양을 읽거나 입력받아 배경·사진·문구·도형·움직임 효과를 얹고 PNG/WebP(움직이는 WebP 포함)로 저장한다. 내장 배경 164장, 부품 아이콘 48개, 샘플 프리셋 18개, 효과 20여 종.

**불편의 구조적 원인.** 소스를 훑어본 결과, 세 가지 불편은 개별 버그보다 구조에서 나온다.

1. **화면이 "기능 분류" 기준이다.** 5개 작업 탭(내용·규격 / 사양 패널 / 이미지 / 배경·테두리 / 텍스트·요소) 아래에 모든 요소의 모든 설정이 긴 스크롤로 항상 펼쳐진다. 요소 하나를 고치려면 그 설정이 어느 탭에 있는지 먼저 알아야 한다. 여기에 "프리셋으로 만들기 / 직접 만들기" 두 모드가 별도 편집 화면으로 겹친다.
2. **요소가 "종류별 고정 칸"에 들어 있다.** 상태가 `rows / texts / stickers / bands / fxs` 묶음(개수 상한 포함)이고, 그리는 순서는 `app.js`(29만 자 단일 파일)의 렌더 함수에 고정돼 있다. 레이어 관리는 v2.0에서 제거됐다. 그래서 위아래 순서를 바꾸거나 "지금 고른 것만 조작"하는 일이 구조적으로 막혀 있다.
3. **값이 조용히 덮인다.** 입력값이 정규화 단계에서 범위 보정(약 100곳)을 거치고, 자동 축소·일괄 적용 같은 상위 설정이 개별 값을 덮는다. 예: 행별 글자색 칸은 다른 탭의 "값 글자색 일괄 적용"을 꺼야 동작하고, 그 안내는 마우스를 올려야 보인다. "수치를 바꿔도 변화 없음"의 주된 출처로 본다(추정).
4. **프리셋과 배경이 따로 논다.** 샘플 18개는 배경 이미지 없이 색·패널·효과로만 구성되고, 배경 164장은 다른 탭의 별도 기능이다. 프리셋을 고른 뒤 배경을 얹으면 글자색·패널이 배경과 맞는다는 보장이 없다(추정).

### 3-2. 코드는 두고 지식만 가져가는 것

기존 앱이 버전을 거듭하며 얻은 교훈이다. 새 코드로 다시 구현하되 같은 시행착오를 반복하지 않도록 요구사항으로 옮긴다.

- **출력 크기 = 카드 크기.** 빛번짐이 카드 밖으로 나가면 투명 여백이 생기고, 디시처럼 투명을 처리하지 않는 곳에서 검은 테두리가 된다. 기본 출력은 카드 경계에서 잘라 정확히 850×300으로 낸다.
- **미리보기와 출력은 같은 렌더러.** 출력 배율(1×/2×/3×)을 바꿀 때 그림자·발광·흐림도 같은 비율로 커져야 한다.
- **사양 자동 읽기 규칙.** Windows가 확실히 알려주는 것만 채운다(PSU·케이스는 빈칸 유지). 사용자가 직접 적은 값은 덮어쓰지 않는다. 적용 전에 결과를 보여준다.
- **부품 라벨 관례.** CPU / MB / RAM / VGA / NVMe·SSD·HDD / PSU / CHA / CS, 한글 이름과 약어 모두 인식.
- **저장 안전.** 임시 파일에 쓴 뒤 교체, 직전 정상본 보관, 자동 복구본, 삭제는 휴지통.
- **실행 취소 범위.** 배경 이미지 교체·프리셋 적용도 한 번의 실행 취소로 되돌아가야 한다. 선택만 바꾼 것은 "수정됨"으로 치지 않는다.
- **움직이는 WebP.** 무손실 프레임의 투명도 플래그, 프레임 수·FPS·예상 용량 사전 안내.
- **효과 기본값.** 낮은 밀도·낮은 속도, 글자 가독성을 해치지 않는 것이 기본.
- **글꼴 준비 후 렌더.** 글꼴 로딩이 끝난 뒤 그려야 첫 화면과 출력이 일치한다.

## 4. 설계 원칙

1. **레이어가 유일한 구조다.** 캔버스에 보이는 것은 전부 레이어 목록에 있고, 목록 위쪽이 화면 앞쪽이다.
2. **선택한 것만 조작한다.** 캔버스 클릭 = 그 위치의 맨 위 레이어 선택. 속성 패널에는 선택한 레이어에 실제로 적용되는 항목만 나온다.
3. **모든 조절은 눈에 보인다.** 값을 바꾸면 화면이 변한다. 다른 설정 때문에 제한되면 그 칸 바로 옆에 이유와 실제 적용값("설정 24px → 자동 맞춤으로 18px"), 한 번에 푸는 버튼을 둔다. 슬라이더 범위는 실제로 차이가 나는 범위와 같게 잡는다.
4. **직접 조작이 먼저, 숫자는 보정용.** 끌어서 옮기고 핸들로 크기·회전, 정밀값은 숫자 칸. 스냅·정렬 가이드 제공.
5. **프리셋은 평범한 문서다.** 편집기에서 만든 디자인을 그대로 프리셋으로 저장할 수 있고, 적용 결과는 일반 레이어다.
6. **미리보기 = 출력.** 한 렌더 함수 `render(문서, 시간, 배율)`가 화면·PNG·WebP 프레임을 모두 그린다.

- **왼쪽 추가 막대**: 텍스트, 이미지, 사양 목록, 도형, 효과. 누르면 레이어가 생기고 바로 선택된다.
- **오른쪽 위 레이어 패널**: 끌어서 순서 변경, 눈(숨김)·자물쇠(잠금), 이름 변경, 복제·삭제, 그룹.
- **오른쪽 아래 속성 패널**: 선택한 레이어 종류에 맞는 항목만. 아무것도 선택하지 않으면 카드 설정(크기·모서리·테두리).
- **프리셋·배경**: 상단 버튼으로 여는 갤러리. 내 현재 내용이 들어간 모습으로 미리 보여준다.
- **첫 실행**: 빈 화면 대신 프리셋 갤러리 → 고르면 사양 입력으로 포커스.

## 6. 문서 모델

```text
문서
├─ 카드: 너비·높이, 모서리 반경, 테두리, 출력 경계
├─ 내용(슬롯 데이터): 사양 행 목록, 닉네임, 대표 이미지
└─ 레이어[] (아래 → 위)
     공통: id, 이름, 표시, 잠금, 불투명도, 혼합 방식,
           위치·크기·회전, 레이어 스타일(그림자·외곽선·발광)
     종류: 배경 채움(색·그라디언트·무늬·이미지)
           이미지(사진·스티커, 자르기·모양 마스크)
           텍스트(가로/세로, 여러 줄, 그라디언트)
           사양 목록(행·라벨·값·아이콘·열 구성)
           도형(사각·원·선·띠)
           효과(절차적 움직임: 반짝임·오로라 등)
           그룹
```

- **내용과 디자인의 분리.** 사양·닉네임·대표 이미지는 "슬롯 데이터"로 따로 두고, 레이어가 슬롯을 가리킨다. 프리셋을 바꿔도 내용이 그대로 따라오는 근거다.
- **사양 목록은 하나의 스마트 레이어.** 행마다 낱개 텍스트 레이어로 풀면 정렬·간격 관리가 사용자 몫이 된다. 한 레이어로 두고 더블클릭으로 행 편집에 들어가며, 행별 색 같은 개별값은 "기본값에서 바뀜" 표시와 되돌리기 버튼을 둔다.
- **저장 형식.** 버전 번호가 있는 JSON + 이미지 파일을 묶은 단일 파일(zip 컨테이너). 이미지를 JSON 안에 문자열로 넣는 방식보다 가볍고 복구가 쉽다.

## 7. 기술 구성

| 항목 | 추천 | 이유 | 대안과 트레이드오프 |
|---|---|---|---|
| 언어·빌드 | TypeScript + Vite | 문서 모델의 형식 오류를 컴파일 단계에서 잡음 | 순수 JS: 설정이 단순하지만 기존 앱과 같은 문제가 반복되기 쉬움 |
| UI | React + Zustand(+Immer 패치) | 레이어 끌어 정렬·색상 선택 등 검증된 부품이 많고, 패치 기반 실행 취소가 간단 | Svelte: 코드량이 적지만 편집기용 부품이 적음 |
| 렌더러 | 자체 Canvas 2D 렌더러(레이어별 오프스크린 합성) | 움직임 프레임 출력·배율 출력·레이어 스타일을 한 함수로 통제 | Konva.js: 핸들·히트 테스트를 바로 얻지만 문서 모델이 라이브러리 노드에 묶이고 프레임 단위 출력이 번거로움 |
| 데스크톱 포장 | Electron 포터블 | 이 PC에 도구가 이미 갖춰져 있고(Node 24) 개발 브라우저와 엔진이 같음 | Tauri: 실행 파일이 훨씬 작지만 Rust 설치가 필요(현재 미설치) |
| 움직이는 WebP | 프레임별 인코딩 후 컨테이너 조립 | 추가 설치 없이 가능할 것으로 예상(0단계 스파이크에서 확인) | libwebp WASM: 품질 제어가 좋지만 번들이 커짐 |
| 시스템 글꼴 목록 | Local Font Access API | 설치된 글꼴을 이름으로 고름(0단계에서 Electron 동작 확인) | 글꼴 이름 직접 입력: 단순하지만 불편 |

배경 원본 298MB는 새 저장소에 싣지 않고 변환본만 싣는다. 기존 포터블 EXE가 404MB였던 주원인이 PNG 원본 내장이었다.

## 8. 주의점

1. **범위 팽창.** 기존 앱은 효과 20여 종·프리셋 18개·웹 배포까지 넓어졌다. 새 앱은 "레이어 편집 → PNG 출력"이 끝까지 되는 세로 한 줄을 먼저 완성하고 넓힌다.
2. **포토샵을 만들지 않는다.** 850×300 한 장, 레이어 수십 개가 대상이다. 브러시·필터·마스크 편집 같은 범용 기능은 범위 밖.
3. **시간 축은 처음부터.** 움직임은 5단계에서 구현하지만 렌더 함수는 1단계부터 시간 값을 받는다. 나중에 끼워 넣으면 렌더러를 다시 써야 한다.
4. **사양 목록의 자동 맞춤.** 패널에 안 들어갈 때 글자를 줄이는 기능은 유지하되, 줄어든 실제 크기를 속성 패널에 표시한다.
5. **끌기 한 번 = 실행 취소 한 번.** 끄는 동안의 중간값은 이력에 쌓지 않는다.
6. **성능.** 발광·흐림은 레이어별로 캐시하고, 바뀐 레이어만 다시 그린다.
7. **브랜드 배경 48장.** 제조사 문장·이름을 소재로 한 이미지라, 공개 배포판에 넣을지는 배포 결정 때 따로 판단한다. 개인 사용에는 영향 없음.
8. **기존 앱은 건드리지 않는다.** 기존 폴더는 읽기만 하고, 변환 결과는 새 프로젝트에 만든다.

## 10. 검증 방법

- **속성 반영 검사(핵심).** 레이어 종류별 모든 속성에 대해 "값 변경 → 렌더 → 픽셀 차이 존재"를 자동 검사한다. 조건부 속성은 선행 조건을 명시해 함께 검사한다. "수치를 바꿔도 변화 없음"을 회귀 테스트로 막는 장치다.
- **기준 이미지 비교.** 대표 문서 몇 개의 출력 이미지를 기준본과 비교(1×/2×, 정지/움직임 첫 프레임).
- **문서 모델 단위 테스트.** 레이어 추가·삭제·순서 변경·실행 취소·저장 후 다시 열기.
- **실제 조작 확인.** 단계가 끝날 때마다 앱을 띄워 끌기·핸들·레이어 순서 변경을 직접 조작하고 화면으로 확인.
